# Canonical Data Model

Week 6 adds a derived canonical normalization layer on top of the evidence-backed
facts collected in Weeks 3-5. The source facts remain in `ProductSpecification`,
`Evidence`, `SourceDocument`, `SKU`, `ServiceTier`, Region, and availability
tables. Canonical rows are reproducible and may be deleted and regenerated by
`normalization_run`.

## Tables

| Table | Purpose |
| --- | --- |
| `canonical_field_definition` | Stable cross-provider field registry. |
| `normalization_rule` | Versioned legacy-field to canonical-field mapping and unit rule metadata. |
| `normalization_run` | Audit row for one standardization execution. |
| `normalized_specification` | Derived value linked to a source `ProductSpecification` and `Evidence`. |
| `comparability_assessment` | Field-level readiness judgement between products in the same canonical domain. |

## Governance Metadata

Stage 2 stores prompt-required governance metadata in
`canonical_field_definition.metadata_json` without changing the Week 6 database
schema. Each seeded canonical field records:

- `semantic_group`
- semantic/unit/scope/qualifier/evidence status
- evidence requirement
- review policy
- comparability tier and comparability status
- lifecycle status, deprecation flag, and replacement field code

## Provenance Rules

- Every `normalized_specification` links back to one `ProductSpecification` and
  one `Evidence` row.
- Canonical values do not replace raw or parser-normalized values.
- Unit conversions are rule-backed and retain `conversion_notes` when ambiguity
  exists.
- `comparability_assessment` is not a product mapping, competitive score, or
  sales claim. It only records whether a canonical field is ready for later
  comparison.
